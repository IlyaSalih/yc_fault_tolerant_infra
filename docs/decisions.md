Архитектурные и технические решения

Формат: контекст → решение → последствия/альтернативы. По каждому пункту — почему сделано именно так, а не иначе.

1. Сегментация сети: приватные vs публичные подсети

Контекст: задание требует, чтобы web/Prometheus/Elasticsearch были в приватных подсетях, а Grafana/Kibana/ALB — в публичной.

Решение: один VPC, три подсети (публичная + 2 приватные в разных зонах доступности для web-серверов), NAT-шлюз для исходящего трафика из приватных подсетей.

Последствия: приватные ВМ недоступны напрямую с локальной машины — любое администрирование (SSH, curl к внутренним сервисам) идёт только через bastion или изнутри VPC. Это осознанный компромисс безопасности, отражающий требование задания.

2. Bastion как единственная точка SSH-входа

Решение: отдельная ВМ с публичным IP, единственный открытый порт — 22. Все прочие security groups разрешают входящий SSH только из SG бастиона.

Последствия: каждое SSH-подключение к приватным ВМ идёт через -J (ProxyJump) или ProxyCommand. При первом входе на новую ВМ после пересоздания встречается предупреждение о смене host key (ожидаемо после terraform destroy/apply, чистится через ssh-keygen -R <ip>).

3. Preemptible (spot) ВМ почти везде

Решение: большинство ВМ инфраструктуры — preemptible, для снижения стоимости учебного стенда, который поднимается только на время работы над проектом.

Альтернатива, которая не выбрана: отдельно выделять non-preemptible для сервисов с данными (Elasticsearch) не делалось — данные логов не критичны для целостности курсовой, в отличие от гипотетического прод-окружения, где это было бы обязательным решением.

4. Terraform remote state в Object Storage

Решение: state хранится в S3-совместимом бакете Yandex Object Storage, а не локально.

Последствия: устойчивость к потере состояния на рабочей машине; возможность пересоздавать инфраструктуру между рабочими сессиями, не теряя историю ресурсов.

5. Пересоздание инфраструктуры между рабочими сессиями

Контекст: постоянно работающая инфраструктура (7 ВМ + ALB) заметно расходует бюджет облака за время работы над курсовой.

Решение: terraform destroy в конце сессии, terraform apply в начале следующей. State и весь код в git позволяют поднять всё заново детерминированно.

Последствия:

IP-адреса всех ВМ меняются при каждом пересоздании → ansible/inventory/hosts.yml генерируется заново скриптом (scripts/generate_inventory.sh), а не хранится в git
Все Ansible-роли должны быть полностью идемпотентны и не полагаться на состояние, оставшееся от предыдущего поднятия — это неоднократно проверено на практике
SSH host keys бастиона и приватных ВМ меняются — учтено в workflow (см. п. 2)
6. Мониторинг: собственный nginx-экспортер логов вместо только stub_status

Контекст: задание требует метрики http_response_count_total и http_response_size_bytes на дашбордах. Стандартный nginx-prometheus-exporter (на основе stub_status) отдаёт только connection-статистику (active/accepted/handled) — этих двух метрик там физически нет.

Решение: добавлена отдельная роль nginx_log_exporter, разворачивающая prometheus-nginxlog-exporter — экспортер, парсящий access.log построчно и отдающий именно http_response_count_total/http_response_size_bytes по статус-кодам. Исходный nginx_exporter (stub_status) оставлен рядом — даёт дополнительные connection-метрики, не дублирует, а дополняет.

Технический нюанс: формат лога в конфиге экспортера (format = "combined") в использованной версии (v1.11.0) не распознаётся как именованный пресет — требуется явная строка формата ($remote_addr - $remote_user [$time_local] "$request" ...), совпадающая с реальным log_format combined в nginx.

7. Мониторинг: кастомный дашборд вместо только community-дашбордов

Контекст: community-дашборды с Grafana.com дают быструю визуализацию, но не гарантируют точного покрытия требований задания (Utilization/Saturation/Errors + конкретные метрики + тресхолды) и подвержены поломкам при обновлении/несовпадении версий.

Решение: написан отдельный JSON-дашборд («Coursework — Custom USE Dashboard»), провижинится через Ansible наравне со скачанными. Явно покрывает: CPU/RAM/диск/сеть (Utilization + Saturation + Errors), nginx_http_response_count_total, nginx_http_response_size_bytes, тресхолды 70% (warning) / 90% (critical) для утилизации ресурсов, 1/5 в секунду для сетевых и HTTP-ошибок.

Последствия: дашборд переживает любой terraform destroy/apply (полностью воспроизводим кодом), не зависит от доступности стороннего сервиса Grafana.com в момент деплоя.

Известное ограничение: community-дашборд «Node Exporter Full» (ID 1860) не рендерит панели из-за несовместимости schemaVersion между версией «latest» с Grafana.com и установленной версией Grafana (ошибка e.replace is not a function). Оставлен как есть — не блокер, так как все требуемые метрики уже покрыты кастомным дашбордом.

8. Логирование: обход блокировки Elastic для российских IP

Контекст: с 2022 года Elastic ограничил доступ к своим продуктам для пользователей из России и Беларуси в рамках санкционной политики. На практике это выражается в HTTP 403 при обращении к artifacts.elastic.co — как к apt-репозиторию, так и к прямым ссылкам на .deb-пакеты — с IP-адресов российских облачных провайдеров (Yandex Cloud в том числе).

Само задание прямо предвидит эту проблему: «В случае недоступности ресурсов Elastic для скачивания рекомендуется разворачивать сервисы с помощью docker контейнеров, основанных на официальных образах». Этот путь рассмотрен наравне с остальными.

Рассмотренные варианты:

Вариант	Оценка
Docker-контейнеры с официальными образами (рекомендация из задания)	docker.elastic.co подпадает под ту же блокировку, что и artifacts.elastic.co — сам образ всё равно нужно откуда-то стянуть; переносит проблему на Docker Hub/registry, не решая её в корне для этого конкретного случая
Российское зеркало apt-репозитория	Неопределённое доверие и актуальность версий, зависимость от стороннего мейнтейнера
OpenSearch (форк Elasticsearch без ограничений)	Полностью рабочая замена, но задание требует конкретно Elasticsearch/Kibana по названию
Прокси apt-трафика через личный VPS с VPN	Работает, но добавляет постороннюю инфраструктуру в схему курсовой — усложняет объяснение архитектуры
Скачивание .deb локально + доставка через Ansible	Выбрано — доступ к VPN уже есть, .deb скачивается один раз, дальше воспроизводимо без обращения к заблокированным ресурсам при каждом деплое

Решение: пакеты elasticsearch, kibana, filebeat скачиваются один раз локально (с личного VPN) скриптом scripts/download_elastic_debs.sh, кладутся в files/elastic/ (директория в .gitignore — бинарники по 50–600 МБ не годятся для хранения в git), разворачиваются на целевые ВМ через Ansible copy + apt: deb=..., минуя официальный репозиторий полностью.

Последствия: при смене версии Elastic Stack или при клонировании репозитория «с нуля» на новой машине нужно заново прогнать download_elastic_debs.sh (с VPN) перед первым деплоем логирования — это задокументировано в README и в самом скрипте.

9. ELK: отключенный xpack.security

Решение: xpack.security.enabled: false на Elasticsearch, без TLS/аутентификации между компонентами стека.

Обоснование: доступ к Elasticsearch и Kibana и так закрыт на сетевом уровне (security groups — только приватная подсеть + bastion, либо публичный IP Kibana без прямого доступа к ES). Включение security потребовало бы генерации и распространения сертификатов между ES/Kibana/Filebeat — оправданная сложность для прод-окружения, избыточная для учебного стенда с сетевой изоляцией.

Сопутствующее решение: setup.ilm.enabled: false в Filebeat — без этого Index Lifecycle Management тянет за собой дополнительные политики, которые проще избежать при отключенной security-модели. Индексы вместо этого ротируются по дате через имя (nginx-logs-%{+yyyy.MM.dd}).

10. Резервное копирование: единое расписание на все диски

Решение: один ресурс yandex_compute_snapshot_schedule, принимающий список disk_ids, собранный из outputs всех модулей (compute, monitoring, logging) — не привязан к конкретным ВМ по имени.
